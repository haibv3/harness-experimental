# 0008 Cross-Platform Stack: Flutter

Date: 2026-06-05

## Status

Superseded by `0009-hybrid-mobile-desktop-split.md`

## Context

Decision `0007-mobile-desktop-app-focus.md` refocused the harness on
cross-platform mobile (Android, iOS) and desktop (macOS, Linux, Windows) apps
and deferred the stack choice to story `US-019`. This decision executes US-019:
it applies the rubric from 0007, compares candidates, and selects a stack.

Two single-codebase candidates cover all five targets today:

- Flutter (Dart): stable on Android, iOS, and desktop (Windows, macOS, Linux).
- Kotlin Multiplatform (KMP) + Compose Multiplatform (CMP): shares logic across
  all targets; Compose UI for iOS reached Stable in 1.8.0 (2025); desktop runs
  on the JVM (Windows, macOS, Linux).

Verified 2026-06: Compose Multiplatform iOS is Stable; Flutter desktop targets
are stable. Both clear the platform-coverage gate.

### Key assumption

This decision assumes a greenfield project with no strong existing Kotlin/Swift
team bias, prioritizing the fastest reliable path to all five platforms with a
single shared UI and the most mature cross-platform tooling. If that assumption
is wrong, see "Revisit Trigger".

## Decision

Adopt **Flutter (Dart)** as the application stack for all five target platforms,
with a single shared codebase for product logic and UI.

Concrete implications for `docs/ARCHITECTURE.md`:

- `app/` shared layers (`domain`, `application`, `infrastructure`,
  `presentation`) are implemented in Dart.
- The five `surfaces/*` shells collapse into Flutter's per-platform runner
  projects (`android/`, `ios/`, `macos/`, `linux/`, `windows/`) generated by
  `flutter create`, not five separate codebases.
- Local persistence, secure storage, push, and OS capability access go through
  the `infrastructure/platform` adapter layer using Flutter plugins; platform
  channels are the escape hatch for native-only APIs.

Still deferred (not part of this decision):

- Running `flutter create`, build config, CI, and signing setup. Those land with
  the first feature story that needs a runnable app, per the harness scaffolding
  rule.

## Rubric Evaluation

| # | Criterion | Flutter | KMP + Compose |
| --- | --- | --- | --- |
| 1 | Platform coverage (all 5) | All 5 stable | All 5 (iOS UI stable since 1.8) |
| 2 | Codebase model | One codebase, shared UI + logic | Shared logic; shared or native UI |
| 3 | UI consistency vs native feel | Consistent, self-rendered; less native | Native interop easier (SwiftUI/AppKit) |
| 4 | Language/team fit | Dart (new to many) | Kotlin (strong for Android teams) |
| 5 | Ecosystem maturity | Largest cross-platform ecosystem | Growing fast, JetBrains/Google backed |
| 6 | Performance / app size | Good; AOT compiled | Good; desktop bundles a JRE (larger) |
| 7 | Testing story | Widget + integration_test, mature | Kotlin test + Compose UI test, newer |
| 8 | Distribution / update | Well-trodden for all 5 | Mature mobile; desktop JVM packaging |
| 9 | Maintenance / vendor risk | Google-led, large community | JetBrains + Google (KMP) |

Net: Flutter wins on out-of-the-box 5-platform maturity, UI consistency, and
ecosystem breadth. KMP+Compose wins on Kotlin fit and native UI interop.

## Alternatives Considered

1. KMP + Compose Multiplatform. Strong alternative; preferred if the team is
   Kotlin/Android-heavy or native UI interop and smaller desktop footprint
   matter more than ecosystem breadth. Not chosen under the greenfield
   assumption above.
2. Native per platform (Kotlin/Swift/native desktop). Best native feel, highest
   cost; rejected because it multiplies codebases against a single-codebase goal.
3. Web-shell hybrid (Tauri/Electron). Rejected: weaker mobile story for a
   mobile-first product class.

## Consequences

Positive:

- One Dart codebase ships to all five platforms with mature tooling.
- Shared UI reduces parity drift; platform proof focuses on shell behavior.
- Clear mapping from the harness layering to Flutter project structure.

Tradeoffs:

- Dart is a new language for teams without it.
- Self-rendered UI can feel less native, especially on desktop.
- Native-only APIs require platform channels.

## Revisit Trigger

Reopen this decision (new decision record) if any holds:

- The team has significant existing Kotlin/Android or Swift expertise.
- Native UI fidelity or native-component reuse becomes a hard product
  requirement.
- Desktop binary size (JRE-free) becomes a strict constraint favoring KMP/native.
